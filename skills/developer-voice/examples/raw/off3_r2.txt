Review comments, worst first:

**1. SQL injection — blocker.** `"... VALUES ('%s', %s)" % (p['user'], p['amount'])` is string interpolation into SQL. A user named `'); DROP TABLE payments; --` owns your database. Use parameter binding (`db.execute(sql, (user, amount))`) — the driver already does this correctly.

**2. Retrying a bare INSERT double-charges.** If the INSERT commits but the connection drops before the response, the retry inserts *again*. That's a duplicate payment row, i.e. real money. Retries on a write are only safe with an idempotency key + unique constraint (`ON CONFLICT DO NOTHING`), which also needs a unique index on that column.

**3. Failures vanish.** On the final attempt you `print` and fall through — the payment is just missing from `results`. The caller gets a shorter list with no way to know which ones dropped. Return failures explicitly, or raise. This is exactly the class of bug that surfaces as "we lost 40 payments last Tuesday" a month later.

**4. No transaction / no commit.** `db.execute` alone doesn't commit on most drivers. If it does autocommit, say so; if not, this writes nothing. Either way it should be explicit and per-payment, so one bad row doesn't roll back the batch.

**5. `except Exception` retries bugs.** A `KeyError` on `p['amount']` or a constraint violation will never succeed, but you'll retry it 3 times with 7 seconds of sleeping. Catch the driver's transient error type only; let programming errors raise immediately.

**6. `time` isn't imported** — `NameError` on the first failure. And you sleep *after* the last attempt, adding 4 pointless seconds per failed payment.

**7. `print` → `logging`.** No timestamp, no level, no payment ID, no traceback. `log.exception(...)` gives all four.

Minor: `user` is a reserved word in several dialects — quote it or rename to `user_id`. Backoff without jitter means a batch of retries stampedes the DB in lockstep.

Roughly:

```python
def process_payments(payments, db, retries=3):
    """Returns (succeeded, failed); failed is [(payment, exc)]."""
    succeeded, failed = [], []
    for p in payments:
        for attempt in range(retries):
            try:
                with db:  # commit/rollback per payment
                    r = db.execute(
                        "INSERT INTO payments (idempotency_key, user_id, amount)"
                        " VALUES (?, ?, ?) ON CONFLICT (idempotency_key) DO NOTHING",
                        (p["id"], p["user"], p["amount"]),
                    )
                succeeded.append(r)
                break
            except db.OperationalError as e:  # transient only
                if attempt == retries - 1:
                    log.exception("payment %s failed after %d attempts", p["id"], retries)
                    failed.append((p, e))
                    break
                time.sleep(2 ** attempt)
    return succeeded, failed
```

Skipped: jitter, circuit breaker, batching. Add jitter when retry volume is high enough to stampede.
