Review comments, blocking first.

## Blocking

**1. SQL injection (line 6).** `"... VALUES ('%s', %s)" % (p['user'], p['amount'])` interpolates untrusted input into SQL. A user named `x'); DROP TABLE payments; --` owns the database. This needs to be a parameterized query — pass the values as the driver's second argument so it binds them, never format them into the string. This one alone should block the merge.

**2. Retrying an INSERT can double-charge.** If the insert commits and the connection drops before the ack, the retry inserts a second row. On a payments table that's real money. The fix is an idempotency key from the payment plus a unique constraint, with `ON CONFLICT DO NOTHING` (or the equivalent for your DB) so the retry is a no-op. What's the plan for this?

**3. Failures are invisible to the caller.** After the retries are exhausted the loop prints and moves on, so `process_payments` returns a shorter list and no indication of which payments dropped. The caller has no way to reconcile. Return the failures alongside the results (or raise) so the decision belongs to whoever called this.

**4. `except Exception` catches too much.** A `KeyError` on `p['amount']`, a typo in a column name, an `AttributeError` — all get retried three times with backoff, then swallowed. Catch only the driver's transient error class (`OperationalError` / `InterfaceError` or equivalent). Data and programming errors should fail immediately and loudly, since retrying can't fix them.

## Should fix

**5. The last sleep is wasted (line 12).** The sleep runs after the final attempt too, so every permanent failure costs an extra 4 seconds for nothing. Move the sleep into the `else` of the last-attempt check.

**6. `print` instead of logging (line 11).** `print("failed: " + str(e))` loses the stack trace and the payment identity, and it won't reach your log aggregator. Use `log.exception(...)` with the payment ID so a failure is debuggable at 3am.

**7. `time` isn't imported.** As written, the first retry raises `NameError` inside... nothing, because the `except` already fired — it propagates out of the function. Worth a test that exercises the retry path; that would have caught it.

**8. Where's the transaction boundary?** No commit and no rollback appears here. If `db.execute` autocommits per statement, a partial batch leaves half the payments written. If it doesn't, nothing is durable. Either way the intended semantics should be explicit — is a partial batch acceptable?

## Nits

**9. `retries=0` silently skips every payment.** `range(0)` doesn't execute, so the function returns `[]` with no error. A `max(1, retries)` or a validation check makes the contract honest.

**10. No jitter in the backoff.** Fixed `2 ** attempt` means a batch that hits a blip retries in lockstep and hammers the DB in waves. Add a random fraction of a second.

**11. `user` is a reserved word** in Postgres and MySQL. `user_id` avoids the quoting surprise later.

**12. What type is `amount`?** If it's a float anywhere upstream, money is already wrong. Worth confirming it's `Decimal` or integer minor units.

## Sketch

```python
def process_payments(payments, db, retries=3):
    """Insert each payment, retrying transient DB errors.

    Returns (results, failures) where failures is a list of (payment, error).
    """
    results, failures = [], []
    for p in payments:
        for attempt in range(max(1, retries)):
            try:
                results.append(db.execute(
                    "INSERT INTO payments (idempotency_key, user_id, amount)"
                    " VALUES (%s, %s, %s) ON CONFLICT (idempotency_key) DO NOTHING",
                    (p["id"], p["user"], p["amount"]),
                ))
                break
            except db.OperationalError as e:
                if attempt == retries - 1:
                    log.exception("payment %s failed after %d attempts", p["id"], retries)
                    failures.append((p, e))
                else:
                    time.sleep(2 ** attempt + random.random())
    return results, failures
```

The retry-with-exponential-backoff instinct is the right one — everything above is about making it safe to actually retry.
